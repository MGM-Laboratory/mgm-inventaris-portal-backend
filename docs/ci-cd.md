# CI/CD

The workflows below run on pull requests and on merges to `main` of `github.com/MGM-Laboratory/mgm-inventaris-portal-backend`, as the Trigger column of each one says. `main` is protected. Every change goes through a branch, a pull request and the checks, and it is merged with a merge commit, never squash or rebase.

The Go skeleton is in the repository, so the workflow `CI` builds, lints and tests it. The `Dockerfile` in the root builds the image of the service, and `docs-site/Dockerfile` builds the image of the API docs site. Four more workflows build, copy, sign and check those two images. None of the four is a required check, as the section "Docker image workflows" below says.

The job is named `PR format`.                                                                                                                                                                                                                 |

Renovate reads that file, so a bump there is the bump the jobs use. The action `.github/actions/pull-images` sends image pulls through `mirror.gcr.io` and logs in to Docker Hub only when the secret `DOCKERHUB_PULL_TOKEN` exists. The username comes from the variable `DOCKERHUB_USERNAME`.

## Required checks

The ruleset `main` on the default branch requires a pull request with a merge commit, resolved review threads, signed commits, up to date branches, and no deletion or force push. It has no bypass actor. It requires five status checks, each pinned to GitHub Actions.

- Conventional commits
- PR format
- Config gate
- Security gate
- CI gate

A check joins the ruleset after it has run once. The `CodeQL` job is not required by its own name, but its result blocks a merge through `Security gate`, which lists it in `needs`. The pre-commit.ci report and the code scanning results are not required.

A second ruleset, `main-merge-and-approval`, requires one approving review and the approval of a code owner, and it allows only merge commits. It also has the rule `update`, so only the bypass team can merge into `main`. `.github/CODEOWNERS` names the owner. The team `mgm-inventaris-portal-maintainer` can bypass this second ruleset through a pull request, and it cannot bypass the first one. The bypass covers only the approval, the code owner review and the `update` rule. Signed commits, resolved threads, up to date branches and the required checks still apply to the team. A pull request from someone outside the team needs the approval of the owner. A pull request that changes only `go.mod`, `go.sum`, `CHANGELOG.md` or `.release-please-manifest.json` has no code owner, so it needs any one approval.

## Releases

Release Please reads the Conventional Commits on `main` and keeps one release pull request open. Merging it writes `CHANGELOG.md`, creates the tag and publishes the GitHub release. `.release-please-manifest.json` holds the current version, and `release-please-config.json` starts the changelog at the commit named in `bootstrap-sha`.

The private key of the release GitHub App is the secret `RELEASE_APP_PRIVATE_KEY` of the environment `release`, which only `main` can use. The client id is the variable `RELEASE_APP_CLIENT_ID`. Two tag rulesets protect the tags `v*`. `release-tags` blocks deletion, force pushes and updates for everyone, and `release-tags-creation` lets only the release App create a tag.

The release pull request is opened by the App, so the owner can approve it, or a member of the bypass team can merge it like any other pull request. Its title is `chore(main): release X.Y.Z`. Commits of the types `ci`, `docs`, `chore` and `build` do not start a release, and the first `fix` or `feat` after the commit in `bootstrap-sha` does. The first release is 0.1.0, because of `initial-version`. While the version is below 1.0.0, a breaking change raises the minor version and not the major one, because of `bump-minor-pre-major`. The release to 1.0.0 is a decision of the owner.

## pre-commit.ci

The pre-commit.ci GitHub app runs the hooks of `.pre-commit-config.yaml` on every pull request. They check for large files, case conflicts, broken JSON, TOML and YAML, merge conflict markers, symbolic links that do not resolve, private keys, a final newline, mixed line endings and trailing whitespace. The run is not a required check. `autofix_prs` is off, because the ruleset only accepts signed commits and the app would push an unsigned fix. A failing run needs a fix by hand. The app has no setting to turn its update pull requests off, so `autoupdate_schedule` is `quarterly`, the longest interval that it allows. Its update pull request carries unsigned commits and fails the checks `Conventional commits` and `PR format`, so close it. Renovate moves the hook revisions through its `pre-commit` manager, with the commit type `ci`.

## API contract

`openapi.yaml` in the root is the hand written contract of the API. It holds every route of `docs/api.md` with its bodies, its answers and its error codes. The job `OpenAPI lint` in the workflow `Config lint` runs the Redocly CLI on it with the `recommended-strict` ruleset of `redocly.yaml`, which is `recommended` with every warning raised to an error. The job `OpenAPI docs build` builds the docs page from the same file, as the next section says. A spec with an error blocks the merge through `Config gate`. A change to a route updates `openapi.yaml` in the same pull request. The version of the CLI is pinned in one place, `docs-site/package.json` with its lock file, and both jobs and the docs image use it. Renovate keeps it current.

## API docs site

The docs site is one static page that is built from `openapi.yaml` at the address `inventaris-docs.labmgm.org`. The folder `docs-site/` holds everything the build needs. `package.json` and `package-lock.json` pin the Redocly CLI. `finish-page.mjs` runs after the CLI and checks that the page loads nothing from another host. It then writes the `Content-Security-Policy` header of the page as an nginx snippet and a gzip copy of the page. `nginx.conf` and `headers.conf` are the server files of the image, and `Dockerfile` builds it.

The page is built with the viewer inside the file (`--inlineBundle`), so a browser makes no request to a CDN. The font of the page is the system font stack of Redoc, and two small fonts that are embedded in its CSS. The CLI setting `telemetry: off` in `redocly.yaml` also turns off the usage data that the page would send to the vendor. Scripts are allowed only by the hash of their text, and the build makes the hashes on every run, because the page holds the spec and so its hash changes with the spec. Styles need `'unsafe-inline'`, because the page sets style attributes and the viewer adds rules at run time. The one request that the CSP blocks is the small Redocly logo of the sidebar footer, so the text "API docs by" shows without its logo.

The image serves the page at `/`, the raw file at `/openapi.yaml` and an empty `200` at `/healthz` that is not logged. Every other path is a 404. It runs as an unprivileged user on port 8080, and the compose example gives it a read only root file system with one tmpfs on `/tmp`. The job `OpenAPI docs build` runs the same `npm run build` as the image and fails when the page, its gzip copy or the CSP snippet is missing or empty, so a spec that lints but does not build is found before the merge. The Docker workflow builds the image on every pull request, and `Repeatable build` also runs for a change in `docs-site/`, `openapi.yaml` or `redocly.yaml`.

## Naming rules

`.ls-lint.yml` sets the naming of files and folders. Folders are lowercase words joined by hyphens. Files are kebab case, and Markdown files may also use capitals such as `README.md`. A Go file is lowercase words with no separator, and only `_test` may follow them. The folder `internal/database/migrations` has its own entry, which allows exactly `NNNN_title.up.sql` and `NNNN_title.down.sql` with a four digit number and lowercase words joined by underscores. Workflows end with `.yaml` and every other YAML file ends with `.yml`, also when the name has more dots such as `compose.production.yml`, except `.pre-commit-config.yaml`, `openapi.yaml` and `redocly.yaml`, which their tools read by those names. The file `docs-site/Dockerfile.dockerignore` is also excluded, because BuildKit reads the ignore file of a Dockerfile by that name. The folders `docs-site` and `deploy/docs` follow the shared rules. ls-lint does not merge the rules of a folder with the rules above it, so `.ls-lint.yml` repeats the shared rules in every folder entry through a merge key.

## Docker image workflows

`docker.yaml` builds the images, `docker-hub-mirror.yaml` copies them to Docker Hub, `resign.yaml` signs existing images again and `repeatable-build.yaml` checks that two builds give the same files. There are two images. `mgm-inventaris-portal-backend` is built from the `Dockerfile` in the root and lives on GitHub Container Registry as `ghcr.io/mgm-laboratory/mgm-inventaris-portal-backend` and on Docker Hub as `<namespace>/mgm-inventaris-portal-backend`. `mgm-inventaris-portal-docs` is the docs site, built from `docs-site/Dockerfile`, and it lives on GitHub Container Registry as `ghcr.io/mgm-laboratory/mgm-inventaris-portal-docs` and on Docker Hub as `<namespace>/mgm-inventaris-portal-docs`. Both have the same tags, `sha-<commit>` for every push to `main` and the release version for a release tag, and both go through the same scan, SBOM, signature and copy steps. How a host runs them is in [`deployment.md`](deployment.md).

One run of each workflow handles both images with a matrix. The jobs of the service image keep the names they had before the docs image came, which are `Build amd64`, `Build arm64`, `Publish image`, `Copy the image to Docker Hub`, `Sign the image again`, `Build (a)`, `Build (b)` and `Compare the builds`. The docs image adds the jobs `Build docs amd64`, `Build docs arm64`, `Publish docs image`, `Copy the docs image to Docker Hub`, `Sign the docs image again`, `Build docs (a)`, `Build docs (b)` and `Compare the docs builds`. The publish job needs every build job of the run, so a failed docs build also stops the publish of the service image for that run.

**None of the four workflows is a required check, and this change adds no required check to the ruleset.** The required checks stay the five that the section above lists. The jobs `Hadolint`, `Compose config`, `OpenAPI lint` and `OpenAPI docs build` of `Config lint` reach the ruleset through `Config gate`, which lists them in `needs`.

**The build.** The `Dockerfile` has a builder stage on the `golang` image and a runtime stage on `gcr.io/distroless/static-debian13:nonroot`, both pinned by digest. The builder runs on the machine that builds the image and cross-compiles for the target, with `CGO_ENABLED=0`, `-trimpath`, `-buildvcs=false` and an empty build id, so two builds of one commit give the same binary. `GOTOOLCHAIN=local` makes a build fail when the `golang` image is older than the `go` line of `go.mod`, and it never downloads a toolchain. The only input that changes the binary is the build argument `VERSION`. The workflow sets it to the release version for a tag and to `sha-<short commit>` for every other ref. The runtime image holds the binary at `/api`, runs as the user 65532 and has no shell. It has the labels for the source, the license `GPL-3.0-only`, the version and the revision. The health check of the image is the command `api healthcheck`, which asks `GET /healthz` on the health listener inside the container.

**Scan, SBOM and signature.** The publish job scans the amd64 image, and the arm64 image when the run builds it, with Trivy. The scan fails the job for a finding of severity HIGH or CRITICAL that has a fixed version, and it uploads those findings to code scanning. A finding with no fix is not reported. The image already holds its tags when the scan runs, but a failed scan stops the job before the signature, and the Docker Hub copy workflow never copies an image that has no signature. After the scan the job generates a CycloneDX SBOM of the image, attests it for GitHub Container Registry (and for Docker Hub when the variable `DOCKERHUB_USERNAME` is set), and signs the image with keyless cosign in the classic format. A last step verifies the signature against the identity of `docker.yaml`.

**Docker Hub copy.** `docker.yaml` never logs in to Docker Hub, because a pull request can change it. `docker-hub-mirror.yaml` starts when it ends, and GitHub always runs the copy of the mirror that is on `main`. The mirror copies an image only when the signature on it was made by `docker.yaml` on `main` or on a release tag, for the same commit and trigger as the run that started the mirror. For a tag, the commit must also be on `main`. Pull request images and prerelease tags are never copied. The push token is the secret `DOCKERHUB_TOKEN` of the `docker-hub` environment, and the account is the variable `DOCKERHUB_USERNAME`.

**Re-sign.** `resign.yaml` is started by hand with a version such as `0.4.0`, and it runs only on `main`. It checks that GitHub Container Registry and Docker Hub hold the same digest for the tag and that `docker.yaml` attested that digest for the tag `v<version>`. It then signs the image again with the identity of `resign.yaml`.

**Repeatable build.** `repeatable-build.yaml` builds the image twice from one commit on two runners with no cache and writes the result to a folder. It hashes the content of every file and the target of every symlink with `.github/scripts/hash-image-files.sh` and compares the two lists, and it does not compare modes or owners. A pull request runs it when the `Dockerfile`, `.dockerignore`, `go.mod`, `go.sum`, the hash script or the workflow changes, and the weekly run covers the rest, such as a change of the source. No path is ignored, so any difference fails the check, and the job summary lists the paths that differ.

**The docs image.** `docs-site/Dockerfile` has a build stage on the `node` image that runs `npm ci` and `npm run build`, and a runtime stage on `nginxinc/nginx-unprivileged`, both pinned by digest. Its build context is the root of the repository, and `docs-site/Dockerfile.dockerignore` lets only the files that the Dockerfile copies into the context. The image has the same labels as the service image, and its health check asks `/healthz` with the `wget` of Alpine. Trivy uploads its findings under the category `trivy-docs-image-amd64` and `trivy-docs-image-arm64`, so they do not mix with the ones of the service image.

**Not verified yet.** The first run on a pull request built the amd64 image of the service, scanned, attested, signed and verified it, and the two builds of `Repeatable build` matched. The docs image has not run in CI yet, and neither has the matrix form of these workflows. The arm64 build, the run on `main` with its cache, the version tag path, the Docker Hub mirror and the manual `Re-sign image` have not run in this repository. GitHub creates the package of the image as private, so making it public is a step in the browser.

## Dependency updates

Renovate opens the pull requests through the Mend Renovate GitHub app, which an owner of the organization has to install on the repository. `renovate.json` sets a weekly run on Monday before 07:00 Asia/Jakarta, a minimum release age of 7 days, grouped minor and patch updates for Go modules and GitHub Actions, and `go mod tidy` after a Go module update. A major update of a tool version in a workflow waits for approval on the dependency dashboard. The base images of the `Dockerfile` are pinned by digest, and their digest, patch and minor updates arrive in one pull request with the commit type `build`. The base images of `docs-site/Dockerfile` follow the same rule in a group of their own. A new major `node` image and a new minor or major `nginx-unprivileged` image wait for approval on the dashboard, because the second one can move the image from the stable line of nginx to the mainline. The Redocly CLI in `docs-site/package.json` is updated by Renovate with the commit type `build`, together with the lock file. A new minor or major `golang` image waits for approval on the dashboard, because it needs a matching `go` line in `go.mod`. The `go` line itself is raised by hand, so Renovate does not propose it. Dependabot alerts are on and Dependabot security updates are off, so only Renovate opens version pull requests.
